# eBPF Endpoint Detection Engine: Event Schema (v1)

**Status:** draft specification, updated to match the code in `telemetry/` (`src/common.h`, `src/exec_exit.bpf.c`, `src/loader.c`) and one test run. The run covered one kernel and one fixed workload. Behavior beyond it is untested. `file_open`, `net_connect`, and `priv_change` were exercised in a second test run, run 041442 (see Labels), and only the cases that a note cites to that run are Observed. The rest is Planned or Inferred.

**Labels:** *Observed* means seen in the output of the test run `telemetry/tests/out/20261026-021946`, called "run 021946" below (22 checks, 0 failed, kernel 6.6.87.2-microsoft-standard-WSL2, BCC comparison skipped). *Observed* is also used for notes that cite the test run `telemetry/tests/out/20261026-041442`, called "run 041442" (38 checks, 0 failed), and only for `file_open`, `net_connect`, and `priv_change`. Nothing else is labeled Observed. *Planned* is design, or implemented behavior that run 021946 does not show. *Inferred* is believed, not verified, and includes findings that `docs/ARCHITECTURE.md` records from earlier tracing, which are cited by section. Every field below is *Planned* unless a note says otherwise. How these events feed the normalizer and process graph is described in ARCHITECTURE.md sections 3 to 5.

**Layers:** *Planned:* the raw layer is JSON lines printed by the C loader, one UTF-8 object per line. The normalized layer is Python normalizer output, described only as a delta in section 10.

**Sources:** HOOK is a tracepoint argument or field. TASK is a kernel task struct field read through BTF in the eBPF program. PROG is a value the eBPF program computes at event time (clock read, truncation or read status). LOADER is a value generated by the C loader. A required field is always present in events of its type. An optional field may be absent, which means not captured.

## 1. Envelope

Every raw event carries these fields.

| Field | JSON type | Source | Required | Notes |
|---|---|---|---|---|
| `schema_version` | integer | LOADER | required | Major version. The value for this document is 1. |
| `type` | string | PROG tag per hook, rendered by LOADER | required | An event type name from section 2. |
| `ts_ns` | integer | PROG, kernel monotonic clock | required | Not wall-clock time. The normalizer converts it. |
| `pid` | integer | TASK `tgid` (read with the pid/tgid helper) | required | |
| `tid` | integer | TASK `pid` (read with the pid/tgid helper) | required | The kernel's name for the thread id. *Observed:* in all-thread mode, one process produced exit events with four distinct `tid` values. |
| `comm` | string | TASK `comm` | required | *Observed:* the `exec_attempt` for `grep` had `comm` `bash` and the matching `exec_success` had `comm` `grep` (run 021946, events.jsonl lines 2 and 3). |

*Inferred:* a tracepoint's `pid` is a kernel task pid (a thread id), so envelope `pid` and `tid` come from the task and not from the hook argument.

## 2. Raw event types

Tables list fields in addition to the envelope.

### 2.1 `exec_attempt`

*Inferred* (ARCHITECTURE.md section 3.1): `syscalls:sys_enter_execve` fires on every exec attempt, successful or not, exposes `filename` and `argv` as user-space pointers, and carries no result. *Observed:* in run 021946 every `exec_success` had an earlier `exec_attempt` for the same pid, and a nonexistent path produced an `exec_attempt` with no `exec_success` (events.jsonl line 8).

| Field | JSON type | Source | Required | Notes |
|---|---|---|---|---|
| `filename` | string | HOOK `filename`, read by PROG | required | Path as passed. Empty if the read failed (section 5). |
| `filename_truncated` | boolean | PROG | required | |
| `argv` | array of string | HOOK `argv`, read by PROG | required | May be empty. See section 4. |
| `argv_truncated` | boolean | PROG | required | |
| `ppid`, `uid`, `gid`, `start_time_ns` | integer | TASK | required | Section 3. |
| `user_read_failed`, `lossy_encoding` | boolean | PROG, LOADER | optional, always printed | *Observed:* both appear on every `exec_attempt` line in run 021946. |

### 2.2 `exec_success`

*Inferred* (ARCHITECTURE.md section 3.1): `sched:sched_process_exec` fires only on a successful exec and exposes the final filename, `pid`, and `old_pid`, but not `argv`, parent pid, or uid.

| Field | JSON type | Source | Required | Notes |
|---|---|---|---|---|
| `filename` | string | HOOK `filename` | required | Final filename of the executed program. |
| `filename_truncated` | boolean | PROG | required | |
| `old_pid` | integer | HOOK `old_pid` | required | |
| `ppid`, `uid`, `gid`, `start_time_ns` | integer | TASK | required | Section 3. |
| `user_read_failed`, `lossy_encoding` | boolean | PROG, LOADER | optional, always printed | *Observed:* both appear on every `exec_success` line in run 021946. |

This event has no `argv`. *Planned:* the normalizer takes argument data from the matching `exec_attempt`.

### 2.3 `exit`

*Inferred* (ARCHITECTURE.md section 3.1): `sched:sched_process_exit` marks the end of a process, and the exit code and signal have to be read from the task. *Observed:* in all-thread mode the hook produced one event per thread (four exit events, four distinct `tid`, for a process with three extra threads).

| Field | JSON type | Source | Required | Notes |
|---|---|---|---|---|
| `exit_code` | integer | TASK `exit_code` | required | Raw kernel value. See section 9. |
| `exit_status` | integer | LOADER, decoded from `exit_code` | required | See section 9. |
| `exit_signal` | integer | LOADER, decoded from `exit_code` | required | See section 9. |
| `ppid`, `uid`, `gid`, `start_time_ns` | integer | TASK | required | Section 3. |
| `lossy_encoding` | boolean | LOADER | optional, always printed | `exit` carries no `user_read_failed`, because it reads no user-space string. |

**One exit per process.** *Planned:* by default the eBPF program emits `exit` only for the last thread of a process. It detects this by the thread group's live-thread count being zero, and a small map stops two threads that exit together from both reporting. The loader option `--all-thread-exits` (`-t`) reports every thread instead. *Observed:* for a process with three extra threads, default mode produced exactly one exit event and all-thread mode produced four (report.txt lines 20 and 28). The case where the thread group leader exits before the other threads is not tested.

### 2.4 `lost`

A loader-generated report that the ring buffer dropped records. It is not emitted by a kernel hook.

| Field | JSON type | Source | Required | Notes |
|---|---|---|---|---|
| `dropped` | integer | LOADER, from a drop counter | required | Records dropped since the previous `lost` event, or since loader start. |

The envelope of this type is loader-generated: `pid`, `tid`, and `comm` describe the loader process, and `ts_ns` is read by the loader at report time. `lost` carries no identity fields, `user_read_failed`, or `lossy_encoding`. *Planned:* the eBPF program counts failed ring buffer reservations in a per-CPU map and the loader reports increases. *Observed:* run 021946 had no `lost` events, so this path was not exercised. *Planned:* the normalizer treats `lost` as a gap, and any inference across a gap, including `exec_failed`, is unreliable.

### 2.5 `file_open`

*Planned:* the eBPF program attaches to `syscalls:sys_enter_openat` and `syscalls:sys_exit_openat` and filters in the kernel, so only opens of paths on the list in `telemetry/src/sensitive_paths.h` produce an event. The list is the exact paths `/etc/shadow`, `/etc/gshadow`, `/etc/passwd`, and `/etc/sudoers`, the prefixes `/etc/sudoers.d/` and `/root/.ssh/`, and any path of the form `/home/<user>/.ssh/` (the user part is limited by `HOME_USER_SCAN`). Only an absolute path string matches, so a relative path opened through a directory descriptor does not. The `open` and `openat2` syscalls are not hooked. *Inferred* (ARCHITECTURE.md sections 2 and 3.2): the probe still runs on every open, so the filter limits output, not the cost of the probe.

*Planned:* by default the program saves the arguments at entry and reads the path at `sys_exit_openat`, so the record carries `ret`. With the loader option `--file-at-entry` (`-e`) it reads the path at `sys_enter_openat` instead, and the record has no `ret`. The loader prints a `file_stats` line on stderr at shutdown with `mode`, `openat_seen`, `openat_blank` (failed or empty path reads), and `file_open_emitted`, so the two modes can be compared.

*Observed* (run 041442, `file_stats` lines): in entry mode `openat_blank` was 95 of 3094 `openat_seen` in the main run, 28 of 982 in the paired run, and 3 of 115 in the thread run. In exit mode on the same commands it was 0 of 986. The `openat_seen` totals of the two paired runs differ, so they are not the same set of calls. *Inferred* (ARCHITECTURE.md sections 4 and 9): the blank reads at entry are because the memory page is not loaded yet at syscall entry. The run did not test that cause. The cost of exit mode was not measured.

| Field | JSON type | Source | Required | Notes |
|---|---|---|---|---|
| `path` | string | HOOK `filename`, read by PROG | required | Cut at `FILE_PATH_CAP`. Empty if the read failed. |
| `path_truncated` | boolean | PROG | required | |
| `flags` | integer | HOOK `flags` | required | The open flags as passed. |
| `ret` | integer | HOOK `ret` of `sys_exit_openat` | optional | Present by default, absent with `--file-at-entry`. Negative values are errors. *Observed* (run 041442, paired exit-mode run): `/etc/shadow` had a `ret` of zero or more and a missing listed path a negative `ret`. |
| `ppid`, `uid`, `gid`, `start_time_ns` | integer | TASK | required | Section 3. |
| `user_read_failed`, `lossy_encoding` | boolean | PROG, LOADER | optional, always printed | |

### 2.6 `net_connect`

*Planned:* the program attaches to `syscalls:sys_enter_connect`, reads the socket address from user memory, and emits only for address families 2 (IPv4) and 10 (IPv6). Other families are dropped in the kernel. An address shorter than its family's structure is ignored. There is no return value in v1, so a failed connect is reported like a successful one. A connect on a datagram socket is reported too. *Observed* (run 041442): a connect to 127.0.0.1 and a connect to ::1, each to a local listener, were each reported once with the right family, address, and port.

| Field | JSON type | Source | Required | Notes |
|---|---|---|---|---|
| `family` | integer | HOOK address family, read by PROG | required | 2 or 10. |
| `remote_addr` | string | HOOK address, formatted by LOADER | required | Dotted decimal for IPv4, colon text for IPv6. |
| `remote_port` | integer | HOOK address, read by PROG | required | Host byte order. |
| `ppid`, `uid`, `gid`, `start_time_ns` | integer | TASK | required | Section 3. |
| `lossy_encoding` | boolean | LOADER | optional, always printed | Applies to `comm` only. |

### 2.7 `priv_change`

*Planned:* the program attaches to `syscalls:sys_enter_setuid`, `setreuid`, `setresuid`, `setgid`, and `setresgid`. It records the syscall name and the requested ids, not the result, so a call that the kernel rejects is still reported. `setregid`, `setfsuid`, `setfsgid`, `setgroups`, and `capset` are not hooked. This replaces the provisional `old_uid` and `new_uid` fields of an earlier draft, because the hooks see requests, not old and new values. *Observed* (run 041442): `setpriv --reuid` was reported with the requested uid, and a python process that called `setgid`, `setresgid`, `setreuid`, `setresuid`, and `setuid` was reported with those five syscalls in that order and the requested ids.

| Field | JSON type | Source | Required | Notes |
|---|---|---|---|---|
| `syscall` | string | PROG, from the hook | required | One of `setuid`, `setreuid`, `setresuid`, `setgid`, `setresgid`. |
| `ids` | array of integer | HOOK arguments | required | The requested ids in argument order: one for `setuid` and `setgid`, two for `setreuid`, three for `setresuid` and `setresgid`. A value of 4294967295 is the unsigned form of -1, meaning leave unchanged. |
| `ppid`, `uid`, `gid`, `start_time_ns` | integer | TASK | required | Section 3. These are the ids before the call. |
| `lossy_encoding` | boolean | LOADER | optional, always printed | Applies to `comm` only. |

## 3. Process identity

*Planned:* `ppid`, `uid`, `gid`, and `start_time_ns` are required on `exec_attempt`, `exec_success`, `exit`, `file_open`, `net_connect`, and `priv_change`, and with the envelope `tid` and `comm` every process record carries them, following ARCHITECTURE.md section 3.1. *Observed:* run 021946 passed the field check for the first three types. *Observed:* run 041442 passed the same check for all six types.

| Field | Source | Notes |
|---|---|---|
| `ppid` | TASK `real_parent->tgid` | *Observed:* `ls` had the `sh` process as its parent in the shell chain check. |
| `uid` | TASK `real_cred` uid, the real uid | *Observed:* the `exec_success` for a command started through `setpriv` as uid 1000 carried `uid` 1000. The effective uid is not captured (*Planned*). |
| `gid` | TASK `real_cred` gid, the real gid | *Planned.* No test checked a non-root gid. |
| `start_time_ns` | TASK `group_leader->start_time`, on the same monotonic clock as `ts_ns` | *Observed:* the `exec_attempt`, `exec_success`, and `exit` of one process carried the same value (for example pid 5232, lines 2 to 4). It is the start of the thread group leader. |

*Inferred:* pids are reused (stated in ARCHITECTURE.md section 5), so `pid` alone is not a safe key. Behavior under reuse is untested. *Planned:* `start_time_ns` is required in v1 so that `pid` plus `start_time_ns` can key a process node (ARCHITECTURE.md section 5). It was optional in an earlier draft, and it and the `exit` identity fields were made required before any consumer existed.

## 4. `argv` and `envp`

*Planned:* `argv` is an array of strings in the order the caller passed them. `argv_truncated` is true if trailing arguments are omitted or any element was shortened. The loader does not build a command line; the normalizer does.

*Planned:* `envp` is not captured by default and v1 has no `envp` field. *Observed:* no line in run 021946 contained an `envp` field. *Inferred:* the environment often holds secrets such as tokens and passwords. *Inferred:* `envp` is available at the same hook (ARCHITECTURE.md section 10, where capturing it is listed as not yet considered). An opt-in field could be added later without a major version change.

## 5. Truncation, caps, and failed reads

*Planned:* every variable-length field has a boolean flag, true when the value is a prefix of, or is missing data from, the original: `filename_truncated`, `argv_truncated`, and `path_truncated`. *Inferred:* `comm` is bounded by the kernel and has no flag.

**Caps.** *Planned:* the caps are constants in `telemetry/src/common.h`. They are first values chosen without any measurement, and they are to be revisited after measurement.

| Constant | Value | Meaning |
|---|---|---|
| `FILENAME_CAP` | 256 | Bytes of `filename`, including the terminating NUL |
| `ARGV_MAX_ARGS` | 16 | Arguments captured per `exec_attempt` |
| `ARGV_ARG_CAP` | 128 | Bytes per argument, including the NUL (127 bytes of text) |
| `RINGBUF_BYTES` | 4194304 | Ring buffer size (`1u << 22`) |
| `FILE_PATH_CAP` | 256 | Bytes of `path` in `file_open`, including the NUL |
| `FILE_PEEK` | 128 | Bytes of the path the kernel filter examines |
| `HOME_USER_SCAN` | 32 | How far into a `/home/` path the filter looks for `/.ssh/` |

*Planned:* an argument of exactly 127 bytes is also flagged truncated, because the read cannot tell it from a longer one. *Observed:* in run 021946 a call with more than 16 arguments came back with 16 and `argv_truncated` true, a long argument came back cut to 127 bytes with `argv_truncated` true, the burst of 50 short commands had no truncation flag set, and the `python3 -c` script argument was cut and flagged (events.jsonl line 183). *Inferred:* caps must exist because ARCHITECTURE.md section 3.3 calls for fixed-size ring buffer records.

**Failed reads.** *Planned:* if the eBPF program cannot read a user-space string, the required string field is empty and `user_read_failed` is true. *Inferred* (ARCHITECTURE.md sections 4 and 9): paths read at `sys_enter_openat` were sometimes blank in bpftrace, because the memory page was not yet loaded at syscall entry. *Observed:* no event in run 021946 had `user_read_failed` true. That is one workload, so an empty `filename` is still not proof of an empty program name.

## 6. Exec failure

*Planned:* the v1 raw schema has no return code field. The normalizer derives `exec_failed`: an `exec_attempt` is failed if no `exec_success` with the same pid arrives before the next `exec_attempt` or `exit` for that pid. *Observed:* the nonexistent path in run 021946 was the only attempt without a success, and its `exit` followed with `exit_status` 127 (report.txt lines 6 to 9). *Inferred:* a dropped `exec_success` or pid reuse can make this wrong.

*Open question:* a `sys_exit_execve` hook could report the return value instead. It is listed in ARCHITECTURE.md section 10, is untested, and would be additive.

## 7. Versioning

1. *Planned:* `schema_version` is an integer major version.
2. *Planned:* within a major version, changes are additive only: new optional fields and new event types. Fields are never removed, renamed, retyped, or given new meaning, and required stays required. Anything else needs a new major version.
3. *Planned:* consumers ignore unknown fields and unknown event types. The normalizer rejects an unsupported `schema_version`.

## 8. Encoding of non-UTF8 bytes

*Planned:* paths and arguments are byte strings and need not be valid UTF-8, but every line must stay valid JSON. The loader decodes string fields as UTF-8, replaces each invalid byte or sequence with U+FFFD, and sets `lossy_encoding` to true on the event if it replaced anything. The rule is lossy. A lossless companion (for example hexadecimal text of the raw bytes) is left to a later task and would be additive. *Observed:* an argument containing the two bytes `0xff 0xfe` came back as two U+FFFD characters with `lossy_encoding` true, and every line in the run parsed as strict JSON (report.txt lines 1 and 24).

## 9. `exit_code`

*Observed:* `exit_code` is the raw kernel value, with the exit status shifted left by 8 bits and the terminating signal in the low bits. In run 021946, `exit 7` gave `exit_code` 1792 (0x700), a process killed with signal 9 gave `exit_code` 9, and the child of the failed exec gave `exit_code` 32512 (127 shifted left by 8) (report.txt lines 8, 16, and 18).

*Planned:* the loader prints `exit_code` unchanged and adds `exit_status` (`(exit_code >> 8) & 0xff`) and `exit_signal` (`exit_code & 0x7f`). *Observed:* the decoded values matched in those three cases: status 7 and signal 0, status 0 and signal 9, and status 127 and signal 0. *Inferred:* the kernel's core dump flag (bit 0x80) is not decoded, and no test produced it.

## 10. Normalized events, delta only

*Planned:* the normalized layer is written by `normalizer/normalize.py`. It has been exercised by unit tests on constructed fixtures and run over a saved `events.jsonl`, and it has not been part of a recorded pipeline run, so nothing in this section is Observed. Every item can change.

**Stream.** One output line per accepted input line, in input order, with every input field kept unchanged. The one addition to the order is that a derived `exec_failed` event is written immediately before the event that revealed it. The normalized layer uses the same envelope, with `schema_version` 1.

**Added fields.**

| Field | Types | Notes |
|---|---|---|
| `process_key` | all | String `<pid>:<start_time_ns>`, for example `5903:19760834152510`. It is null for `lost` (the pid is the loader's and there is no start time) and for any event whose `pid` or `start_time_ns` is missing or not an integer. |
| `exe` | `exec_attempt`, `exec_success`, `exec_failed` | The `filename`. For an attempt it is the path as passed. For a success it is the final path. |
| `cmdline` | `exec_attempt`, `exec_success`, `exec_failed` | The `argv` elements joined by single spaces with no quoting, so an argument that contains a space cannot be told apart in `cmdline`. `argv` is the exact form. |
| `argv`, `argv_truncated` | `exec_success` | Copied from the matching `exec_attempt`. `argv` is empty when there is none. |
| `attempt_joined` | `exec_success` | True if the argument data came from a pending attempt of the same process key. |
| `exit_status`, `exit_signal` | `exit` | Kept as the loader printed them. If the loader did not give them, they are decoded from `exit_code` as in section 9. |

**Join.** An `exec_success` takes its `argv` from the pending `exec_attempt` with the same process key. This refines section 6, which joins by pid: the key includes `start_time_ns` so that a reused pid is a different process.

**`exec_failed`.** An `exec_attempt` is pending until the next event of its process key. It becomes `exec_failed` if that event is another `exec_attempt` (`reason` is `next_attempt`, the shape of a shell searching PATH) or an `exit` (`reason` is `exit`). An `exec_success` clears it. The event is a copy of the attempt with `type` changed, so it keeps the attempt's `ts_ns`, `filename`, `argv`, `exe`, `cmdline`, and identity fields, plus `reason` and `gap_uncertain`. `gap_uncertain` is true if a `lost` event arrived between the attempt and the decision, because the dropped record could have been the success (section 2.4).

**End of input.** An attempt still pending when the input ends is not turned into `exec_failed`, because the input does not show how it ended and the loader may simply have been stopped before the result. It is counted in the summary as pending. Its `exec_attempt` line was already written, so no information is lost.

**Anomalies.** The normalizer never stops on a bad line. It counts, and prints in the summary: lines that are not a JSON object (`bad_json_lines`), lines that are not valid UTF-8 (`invalid_utf8_lines`, the bad bytes are replaced), a `schema_version` that is missing or not 1 (`unsupported_schema_version`, the event is dropped, as section 7 says), an unknown `type` (`unknown_event_type`, the event is passed through with its `process_key`), a missing identity field (`missing_identity`), a field of the wrong type (`malformed_field`, the value is coerced for `argv` and `filename`), an `exec_success` with no pending attempt (`exec_success_without_attempt`), an `exit` for a key with no exec event (`exit_without_exec`), and an eviction from the tracking table (`state_evicted`). `exit_without_exec` covers two cases the input cannot tell apart: a process that started before the loader, and a process that forked and never called exec. A second `exit` for a key that already exited, as all-thread mode produces, is counted separately as a repeat exit and is not an anomaly. The summary also gives the count of each input type and the total of `dropped` over all `lost` events.

**Bounds.** The tracking table holds at most 65536 processes and drops the least recently used one when full. That value is a first guess and has not been measured.

**Not done.** `ts_ns` is passed through unchanged and is not converted to a wall-clock format, so the format question stays open.

## 13. Process graph

*Planned:* the graph is built by `graph/process_graph.py` from normalized events (section 10). It has been exercised by unit tests on constructed fixtures and run over one saved events file, and it has not been part of a recorded pipeline run, so nothing in this section is Observed. Every item can change. It consumes events and defines no new event type.

**Nodes.** One node per process key. A node holds `pid`, `start_time_ns`, the `ppid` first seen, `uid` and `gid` as first seen, `comm` as last seen, first and last `ts_ns`, an exec history, an exit record, and lists of `file_open`, `net_connect`, and `priv_change` entries. An exec in place (the same key with a second `exec_success`) adds a history entry to the same node, because `pid` and `start_time_ns` do not change across an exec (section 3). A history entry has `exe`, `cmdline`, `ts_ns`, `failed`, and for a derived `exec_failed` also `reason`. An `exec_attempt` is not a history entry. Only its outcome is. The exit record keeps the first `exit` seen, and later ones (all-thread mode) are counted as repeat exits.

**Parent link.** An event gives `ppid` and no parent start time, so the parent is resolved when a node is first created: it is the known process with that pid and the latest `start_time_ns` that is not later than the child's. A candidate that exited before the child started is rejected. *Inferred:* the link can be wrong when pids are reused and the real parent was never seen, and nothing in the input can show that. Each node records how its link was made: `observed` (the parent node already existed), `placeholder`, or `late` (a placeholder later replaced by the real parent). A `ppid` of 0, or of 1 with no known pid 1 node, ends the chain as a root and makes no placeholder.

**Placeholders.** A parent that is not known gets a placeholder node with the key `<pid>:unknown`, no start time, and `placeholder` true. It means the parent started before the loader, forked without an exec, or was never recorded, and the input cannot tell these apart. There is one placeholder per pid. When a real process for that pid is later seen, the placeholder's children that started at or after it move to the real node, and the placeholder is dropped when it has no children left. Placeholders are not evicted.

**Edges.** An edge is made once, when the child node is created. A later event for the node with a different `ppid` (usually a reparent after the parent exited) is added to the node's `ppid_changes` list and no edge is made or changed.

**Queries.** `ancestry(key)` returns the chain, process first, and a stop reason: `root`, `placeholder`, `cycle`, `depth_cap`, `parent_missing` (the parent node was evicted), `no_parent_info` (no `ppid` was recorded), or `unknown_key`. It tracks visited nodes and a depth cap, so it always ends. `children(key)` lists the children in the order first seen. `find_by_pid(pid, ts_ns)` returns the process with the latest start not after `ts_ns`, or none if that process had exited before `ts_ns`.

**Events not attached.** `lost` events are counted, with the total of `dropped`, and belong to no node. An event with no usable `pid` and `start_time_ns` is counted as `missing_identity` and not attached. An event whose `process_key` differs from the key built from its `pid` and `start_time_ns` is counted as `key_mismatch`, and the built key is used.

**Bounds.** All values are first guesses and none has been measured. `MAX_NODES` is 100000: when it is exceeded the oldest exited nodes are evicted first, and a live node is never evicted, so the graph can stay over the limit (counted as `over_limit_while_live`). A child of an evicted parent keeps its parent key, and ancestry stops with `parent_missing`. `MAX_EVENTS_PER_LIST` is 200 for each list of each node: the first entries are kept and the rest are counted as dropped, per node and in total. `MAX_ANCESTRY_DEPTH` is 64.

**Anomalies.** Counted and never fatal: `bad_json_lines`, `invalid_utf8_lines`, `not_an_object`, `unsupported_schema_version` (the event is skipped), `unknown_event_type`, `missing_identity`, `key_mismatch`, `malformed_field`, and `ppid_missing`. The summary also gives node, edge, placeholder, exited, and evicted counts, edges by link kind, drops per list, and events by type.

**Not done.** Edges from a process to files and sockets are stored as per-node lists and not as separate nodes. Querying children within a time window is not implemented. A window can be applied to the child list by the caller using each child's first-seen time. Detections and alerts are not part of the graph.

## 14. Alerts

*Planned:* the alert format is defined by `alerts/alert.py`. It has been exercised by unit tests on constructed fixtures and by one alert built from a saved events file with a test-only trigger, and it has not been used by any detection or in a recorded pipeline run, so nothing in this section is Observed. Every item can change. No detection, technique mapping, suppression, or wall-clock conversion exists.

**Stream.** One JSON object per line, ASCII-safe, keys sorted, no NaN or Infinity. A second rendering gives the same information as readable lines. The sink can disable either output. An alert that cannot be encoded as strict JSON is counted and skipped.

**Fields.**

| Field | JSON type | Notes |
|---|---|---|
| `alert_schema_version` | integer | 1. Versioning follows section 7. |
| `alert_seq` | integer | Per-run sequence starting at 1, stamped by the sink when the builder left it null. No random ids, so the same input gives the same output. |
| `detection` | string | The name the detection passes in. |
| `technique` | string or null | Always null for now. *Planned:* the ATT&CK mapping is a separate task (ARCHITECTURE.md section 6), so no technique id is invented here. The readable form says "technique unassigned". |
| `ts_ns` | integer or null | The `ts_ns` of the triggering event, kernel monotonic time, not wall-clock. The conversion is an open question (section 10) and is not decided here. |
| `process` | object | `process_key`, `pid`, `ppid`, `comm`, `exe`, `cmdline`, `uid`, `gid`, and `placeholder`. `exe` and `cmdline` are from the latest entry of the node's exec history. A value that is unknown is null. |
| `ancestry` | array of object | The graph's chain, process first, each entry shaped like `process`. A placeholder parent has `placeholder` true and null fields. Capped at `MAX_ANCESTRY_ENTRIES` (32, unmeasured). |
| `ancestry_stop` | string | The graph's stop reason from section 13, or `unknown_key` when the process is not in the graph. |
| `evidence` | array of object | Deep copies of the events that fired the rule, in the order given. Capped at `MAX_EVIDENCE_EVENTS` (10, unmeasured). |
| `evidence_dropped` | integer | How many evidence events were beyond the cap. |
| `data_quality` | object | See below. |

**`data_quality`.** `lost_events_seen` is the number of `lost` events the graph has counted in the whole run so far, not only for this process, because a `lost` event names no process. `ancestry_complete` is true only if `ancestry_stop` is `root` and the chain was not cut by the cap. `ancestry_truncated` is true if the cap cut the chain. `process_in_graph` is false if the triggering process has no node, in which case `process` is filled from the triggering event only and `ancestry` is empty.

**Readable form.** In order: detection name and technique, `ts_ns`, the process with its command line, the ancestry as a chain, the evidence in a short form, then warning lines for a process missing from the graph, incomplete ancestry, and lost events. Text from events is escaped (control characters and non-ASCII), so a command line cannot change the terminal.

**Viewer.** `alerts/alert.py` reads alert lines from a file or standard input and prints the readable form. Lines that are not JSON objects are skipped and counted.

## 15. Detection `shell_from_service` and the runner

*Planned:* the detection is `detections/shell_from_service.py` and the runner is `detections/runner.py`. *Observed* in this section means seen in the runner's output on the saved normalized events file of the final eb-tel2 evidence; it is not one of the runs named under Labels. *Observed:* the live test of this section was run under sudo, and the saved report in the evidence-eb-d1 folder shows 19 checks, 0 failed. It defines no new event type.

**Rule.** A shell is a process whose `exec_success` has an executable basename in `SHELL_NAMES`: `sh`, `bash`, `dash`, `zsh`, `ash`, `ksh`, `csh`, `tcsh`, `fish`. The detection fires when the graph node of that shell has a direct parent node whose `comm` is in `SERVICE_NAMES` (`nginx`, `apache2`, `httpd`, `mysqld`, `postgres`, `redis-server`, `mongod`) or starts with `php-fpm`. `sshd`, `systemd`, `cron`, and `login` are left out because they start shells legitimately. Both lists are constants at the top of the file, are an inferred list of names, and can be edited. *Inferred:* `comm` is the executable's file name cut to 15 characters by the kernel and is not `argv[0]`, so a renamed or copied binary takes the new name. The parent's `comm` is the one last seen in the graph when the shell's `exec_success` arrives, and after an exec in place that is the new program's name. A service that executes a shell in place is the shell, so its own parent is judged and not the service.

**Output.** One alert per qualifying `exec_success`, with no dedup. Section 14 gives the fields. The name is `shell_from_service` and `technique` is null, because no technique id has been assigned: the ATT&CK mapping is a separate task. The evidence is the `exec_success` (which carries `argv` and `cmdline`) and the latest `exec_attempt` of the same process key if the runner still holds it. The runner keeps at most `MAX_PENDING_ATTEMPTS` (4096, unmeasured) attempts and drops the oldest.

**Unevaluable.** If the parent cannot be judged, no alert is raised and the case is counted as unevaluable with a reason: `placeholder_parent` (the parent was never seen), `no_parent` (the ppid is 0 or 1 with no known node, or missing), `parent_missing` (the parent node was evicted), `parent_no_comm`, or `shell_not_in_graph` (the event had no usable identity). *Observed:* on the saved file the runner counted 3 unevaluable shells, all `placeholder_parent`, which are the three `sh -c` commands of the test workload whose parent shell started before the loader.

**Limitations.** Legitimate services sometimes run shells (CGI scripts, piped logging, maintenance hooks), so the rule will raise false positives on such systems. It misses a shell started by a service under a name that is not on the list, a shell reached through another interpreter, and a shell whose parent was never seen. None of these rates has been measured.

**Runner.** For each input line the runner ingests the event into the graph first, then calls each detection as `detect(graph, event, ctx)`, which returns an alert dict or None, then emits the alert through the sink from section 14. The detections are a plain list in the runner. The order of the input is kept. An exception in a detection is counted and the stream goes on. Events with a `schema_version` other than 1 are not passed to detections. It reads a file or standard input, so it can end a pipe: loader, normalizer, runner. When reading standard input it ignores SIGINT so that it ends at the end of input, as the normalizer does. At the end it prints to standard error: events processed, alerts emitted per detection, unevaluable counts, detection errors, a graph summary line, and the lost-event count. *Observed:* on the saved file it processed 313 events and emitted 0 alerts, with 3 unevaluable. That file has no service parents, so zero alerts is expected and says nothing about the false positive rate in real use.

**Live test.** `detections/tests/live_test.sh` is written to run the pipeline under sudo with a copy of bash named `nginx` that forks a child shell, a copy with a name not on the list, and an ordinary shell command, and `validate_live.py` checks the saved output. *Observed:* it was run under sudo, and the saved report in the evidence-eb-d1 folder shows 19 checks, 0 failed.

## 16. Detection `exec_from_tmp`

*Planned:* the detection is `detections/exec_from_tmp.py`, registered in the runner of section 15 after `shell_from_service`. *Observed* in this section means seen in the runner's output on two saved normalized events files: the final eb-tel2 evidence and the saved output of the eb-d1 live test. *Observed:* the live test of this section was run under sudo, and the saved report in the evidence-eb-d2 folder shows 26 checks, 0 failed. It defines no new event type.

**Rule.** The trigger is an `exec_success` whose `filename` is absolute and, after cleanup, lies under a directory in `SUSPECT_DIRS`: `/tmp`, `/var/tmp`, `/dev/shm`. The list is a constant at the top of the file and can be edited. Cleanup is lexical: repeated slashes are collapsed and `.` and `..` are resolved (`posixpath.normpath`), and a leading `//` or `///` is also collapsed to one slash, because Linux reads `//tmp/x` as `/tmp/x` while `normpath` keeps exactly two leading slashes. The path matches only if it starts with the directory followed by a slash, so `/tmpfoo/x`, `/var/tmpfoo/x`, `/tmp` itself, and `/tmp/../usr/bin/x` do not match, and `/usr/bin/../../tmp/x` does. The cleanup uses no file system, so a symlink is not followed.

**Output.** One alert per qualifying `exec_success`, with no dedup and no allow list. Section 14 gives the fields. The name is `exec_from_tmp` and `technique` is null, because no technique id has been assigned: the ATT&CK mapping is a separate task. The evidence is the `exec_success` and the latest `exec_attempt` of the same process key if the runner still holds it, as in section 15. A failed exec has no `exec_success`, so it does not alert.

**Unevaluable.** No alert is raised and the case is counted with a reason: `read_failed` (`user_read_failed` is true), `no_filename` (missing, empty, or not a string), `relative_path` (the filename does not start with `/`, and the data has no working directory to resolve it), or `truncated` (`filename_truncated` is true and the kept prefix is not already under a suspect directory). A truncated filename whose kept prefix is already under a suspect directory alerts. *Inferred:* the prefix can be misleading, because a `..` in the part that was cut could lead out of the directory. The reasons are summarized by the runner together with those of `shell_from_service`. *Observed:* the runner counted no `relative_path`, `no_filename`, `read_failed`, or `truncated` case on either saved file.

**Gaps, not fixed.** An interpreter running a script from these directories (the exec is the interpreter, so the script path is only in `argv`), symlinks, memfd or fd-based execution, relative paths, and a shell that changes into one of these directories first and runs a relative path. Installers, package scripts, and build tools legitimately execute files from these directories, so false positives are expected on such systems. None of these rates has been measured. *Planned:* the evaluation task measures false positives.

**Observed on saved files.** On the final eb-tel2 evidence file the runner processed 313 events and emitted 0 alerts from either detection, with 3 unevaluable (`placeholder_parent`). That workload ran no file from a suspect directory, so zero alerts says only that the rule did not fire on those events. It says nothing about the false positive rate or the detection rate in real use. On the saved eb-d1 file the runner processed 34 events and emitted 3 alerts: 2 `exec_from_tmp`, for the copies of bash named `nginx` and `evt_notaservice` that the eb-d1 live test executed from a temporary directory under `/tmp`, and 1 `shell_from_service`. Its 1 unevaluable case was a `placeholder_parent`.

**Live test.** `detections/tests/live_test_tmp.sh` is written to run the pipeline under sudo with copies of `/bin/true` executed from `/tmp`, `/var/tmp`, `/dev/shm`, and a control directory under `/opt`, plus a relative-path run and a failed exec under `/tmp`. `validate_live_tmp.py` checks the saved output. *Observed:* it was run under sudo, and the saved report in the evidence-eb-d2 folder shows 26 checks, 0 failed.

## 17. Detection `download_chmod_exec`

*Planned:* the detection is `detections/download_chmod_exec.py`, registered in the runner of section 15 after `exec_from_tmp`. *Observed* in this section means seen in the runner's output on saved normalized events files (the final eb-tel2 evidence and the saved eb-d1 and eb-d2 outputs) or in the saved eb-d2 events. *Observed:* the live test of this section was run under sudo, and the saved report in the evidence-eb-d3 folder shows 32 checks, 0 failed. It defines no new event type.

**Inference.** The telemetry has no chmod event and no file-write event, so the chain is inferred from three `exec_success` events and their `argv`: a download step (`curl` or `wget`), a chmod step (`chmod`), and an exec of the downloaded path. The alert is raised at the final exec, once per `exec_success`, with no dedup and no allow list.

**Download step.** The executable basename is `curl` or `wget`, and the output path comes from `argv`. *curl:* `-o FILE`, `-oFILE`, `--output FILE`, `--output=FILE`, flag clusters such as `-sSLo FILE`, and `-O` or `--remote-name` (the last path segment of the URL, saved in the current directory). *wget:* `-O FILE`, `-OFILE`, `--output-document FILE`, `--output-document=FILE`, `-P DIR`, `--directory-prefix DIR` and `=DIR`, and with no output option the last path segment of the URL without query or fragment (`index.html` if it ends in a slash), saved in the current directory or in the prefix. An output of `-` means stdout and is not tracked. A curl run with no output option also writes to stdout and is counted the same way. The runner's summary does not print this count (`download_to_stdout` in the detection's counters). A command whose path cannot be parsed is ignored and counted as unevaluable with the reason `download_unparsed`. Not handled: curl `--output-dir` and `--create-dirs`, a URL without `://`, several URLs paired with several output options, wget `--input-file`, and a flag cluster that contains a letter this parser does not know takes no value.

**Chmod step.** The executable basename is `chmod`. The first argument that is not an option is the mode and the rest are targets. A mode makes a file executable if it is symbolic and a clause adds or sets `x` (`+x`, `a+x`, `u+x`, `ug+x`, `=rwx`, `a=rx`), or octal with 3 or 4 digits where the user, group, or other digit is odd. *Inferred:* for a 4 digit mode only the last three digits count, because the first digit holds setuid, setgid, and sticky bits and not execute, which differs from counting any digit. `X` is not counted. Options are skipped, so `chmod --reference=FILE` is not handled. A chmod is kept only if it names a path that has an earlier download entry, and only the first one after the download is kept.

**Exec step and matching.** The `filename` of an `exec_success` is cleaned with the lexical cleanup of section 16 if it is absolute, and compared with the tracked paths. Absolute paths match globally. A relative path (`./name` or a bare name, normalized lexically) matches only if the download, the chmod, and the exec were run by processes with the same parent node; the key of a relative entry includes the parent's process key. If the acting process has an unknown or placeholder parent, the relative case is counted as unevaluable with the reason `relative_unknown_parent`: at a download or an executable-making chmod step, and at a final exec only when its name equals a tracked relative name. A final exec with a truncated or unreadable filename is not matched and not counted.

**Order and window.** The download `ts_ns` must be less than the chmod `ts_ns`, which must be less than the final exec `ts_ns`, and the final exec must come within `CHAIN_WINDOW_NS` of the download. A new download of the same path replaces the entry and starts a new chain.

**Bounds.** All values are first guesses and none has been measured: `CHAIN_WINDOW_NS` is 600 seconds, `MAX_TRACKED_PATHS` is 4096 (the oldest download is evicted first), and `MAX_STORED_ARGV_CHARS` is 1024 characters of `argv` and `cmdline` kept per stored event (a cut copy carries `stored_text_cut_by_detection`).

**State.** Held in the run's `ctx` under `ctx["state"]["download_chmod_exec"]`, so the result depends only on the event stream. No wall-clock or random value is used.

**Output.** The name is `download_chmod_exec` and `technique` is null, because no technique id has been assigned: the ATT&CK mapping is a separate task. The evidence is three events in order: the downloader `exec_success`, the chmod `exec_success`, and the final `exec_success`. Section 14 gives the other fields.

**Limitations.** Legitimate install scripts download a file, run `chmod +x`, and run it, and match this rule exactly, so false positives are expected, and the evaluation task measures them. Gaps, not fixed: downloads by tools other than curl and wget, `/dev/tcp` and script-level downloads, pipe-to-shell (no file), chmod through an interpreter, `install -m`, a shell redirection that writes the file, a file renamed after download, `chmod --reference`, an interpreter running a downloaded script (the exec is the interpreter), and a final exec whose filename is truncated.

**Observed on saved files.** *Observed:* the runner processed the final eb-tel2 evidence (313 events), the eb-d1 output (34 events), and the eb-d2 output (28 events) with all three detections registered and emitted no `download_chmod_exec` alert on any of them; none of the three files contains a `curl`, `wget`, or `chmod` exec. Zero alerts there says only that the rule had nothing to match. It says nothing about the false positive rate or the detection rate in real use. In the saved eb-d2 events the loader recorded `./evt_d2_true_rel` as the `filename` of both the `exec_attempt` and the `exec_success` of a program run by relative path, so the working directory is not in the data and a relative filename cannot be resolved.

**Live test.** `detections/tests/live_test_chain.sh` is written to run the pipeline under sudo with a local web server on 127.0.0.1, chains by curl, wget (if installed), and a relative name, and three controls, and `validate_live_chain.py` checks the saved output. *Observed:* it was run under sudo, and the saved report in the evidence-eb-d3 folder shows 32 checks, 0 failed.

## 18. Detection `unusual_ancestry`

*Planned:* the detection is `detections/unusual_ancestry.py`, registered in the runner of section 15 after `download_chmod_exec`. *Observed* in this section means seen in the runner's output on four saved normalized events files (the final eb-tel2 evidence and the saved eb-d1, eb-d2, and eb-d3 outputs). No live run of this detection has been done, so it has not been seen firing on kernel events. It defines no new event type.

**Rule.** The trigger is an `exec_success` whose executable basename is a watched program: a shell (a name in `SHELL_NAMES` of section 15), an interpreter (a name that starts with `python`, or `perl`, `ruby`, `php`, `node`), or a network tool (`nc`, `ncat`, `netcat`, `socat`). The lists are constants at the top of the file and can be edited. The detection fires when any node above the process in the graph's ancestor chain, at any depth within that chain, has a `comm` that matches the service list of section 15 (the same constants and matching logic, `php-fpm` by prefix). The process itself is never counted as an ancestor, so a service that executes a watched program in place is judged by its own parent, consistently with section 15. *Inferred:* the rule is name-based, so it is narrower than the roadmap's word "unusual".

**Overlap with `shell_from_service`.** If the watched program is a shell and the matching service is its direct parent, this detection does not alert, because section 15 owns that case. A shell below a shell below a service raises `shell_from_service` for the first shell and `unusual_ancestry` for the second.

**Unevaluable.** No alert is raised and the case is counted with a reason: `not_in_graph` (the process has no node), or `ancestry_incomplete` (no service was found in the chain and the graph's stop reason is anything other than `root`: `placeholder`, `depth_cap`, `cycle`, `parent_missing`, or `no_parent_info`). A chain that reaches `root` with no service is not an alert and is not counted. A placeholder has no `comm`, so it is never matched as a service. The reasons are summarized by the runner with those of the other detections.

**Output.** One alert per qualifying `exec_success`, with no dedup and no allow list. Section 14 gives the fields, and the alert already carries the ancestry chain and its stop reason. The name is `unusual_ancestry` and `technique` is null, because no technique id has been assigned: the ATT&CK mapping is a separate task. The evidence is the `exec_success` and the latest `exec_attempt` of the same process key if the runner still holds it, as in section 15.

**Limitations.** Gaps, not fixed: a service under a name that is not on the list; a daemon that double-forks and is reparented to pid 1, which loses its service ancestor; a renamed interpreter (an interpreter name that is not on the list, such as `nodejs`, is not watched); `comm` truncation to 15 characters; and the graph's depth cap and placeholders, which hide an ancestor. Legitimate services run interpreters (for example a web server that starts a Python or PHP worker), so false positives are expected, and the evaluation task measures them.

**Observed on saved files.** *Observed:* the runner processed the final eb-tel2 evidence (313 events), the eb-d1 output (34), the eb-d2 output (28), and the eb-d3 output (67) with all four detections registered and emitted no `unusual_ancestry` alert on any of them. The `ancestry_incomplete` count was 7, 2, 0, and 1 on those files. These workloads contain at most one process named `nginx`, made for the eb-d1 test, and it ran a shell as a direct child, which belongs to `shell_from_service`. Zero alerts there says only that the rule had nothing to match. It says nothing about the false positive rate or the detection rate in real use.

**Live test.** `detections/tests/live_test_ancestry.sh` is written to run the pipeline under sudo with python3 run below a copy of bash named `nginx` as a direct child and as a grandchild through `sh`, the same below a copy with an unlisted name, a non-watched program below the `nginx` copy, and a plain python3, and `validate_live_ancestry.py` checks the saved output. It has not been run. The checks were run only against constructed events.
